# ssh_shell session authorization — implementation plan (Plan 3)

## Goal

Enforce the host authorization gate for `ssh_shell` and `ssh_scp`, and add the
dedicated approval card that lets the human allow a host for this session. Spec
§11 and §11.1 are the design.

## Non-negotiables

- `host.approval` is `trusted` (never ask) or `session` (default; ask once per
  session, then remember in memory). No disk/project grants, no per-call-only
  policy in 0.8.0.
- Grants live in a `WeakMap<Session, Set<fingerprint>>`; never written to disk,
  never shared across sessions, lost on plugin reload. A new session asks again.
- Fingerprint = alias + host + port + user + keyPath + passphraseEnv. Any edit
  invalidates the grant.
- The gate runs BEFORE any connection or channel: broken registry/unknown alias
  fail first; then the grant; then dial/exec/scp.
- On a miss call `ctx.approval.request({agent, toolName, callId, reason,
  displayReason, signal})`. The request is the single action "authorize this
  session's use of this host". `allowed-once` records the grant and proceeds;
  `rejected`/`cancelled` throw without connecting; `unavailable` fails closed
  naming the missing answerer and the `trusted` escape hatch; a session approval
  policy of "never" rejects deterministically.
- Concurrent misses for the same host in one session share ONE in-flight
  approval promise.
- Error phase `approval` for gate failures (structured for ssh_scp, thrown for
  ssh_shell; same wording).
- The dedicated card is a `conversation.composer` chain entry at priority 0 that
  only matches pending approvals whose toolName is `ssh_shell` or `ssh_scp`;
  everything else falls through to ui-approval. Buttons answer
  `allowed-once`/`rejected`; no new RPC and no change to approval events.
- The card is reimplemented with the plugin's existing React/ui-primitives
  conventions; do not vendor Apache-2.0 source.
- terminal stays out of scope in 0.8.0.

## Tasks

### Task 1 — grant store + fingerprint + gate core

- New `lib/ssh-shell/approval.js`: `fingerprintOf(host)`,
  `createApprovalGate({ request, logger })` with `authorize({ session, host,
  toolName, callId, signal })`.
- `trusted` bypasses; `session` consults the WeakMap; a hit resolves; a miss
  calls `request` once and records on `allowed-once`.
- In-flight coalescing per (session, fingerprint): concurrent misses await the
  same promise; the promise is deleted in `finally` so a later miss can ask
  again after rejection.
- Reject/cancel/unavailable produce a named error with phase `approval`,
  alias and the host description; never logs key material.
- Unit tests with a fake `request`: trusted no-call; first miss asks once; second
  call same session no ask; a second session asks again; rejection/cancellation/
  unavailable fail closed; `never` policy rejects; fingerprint change re-asks;
  concurrent misses => one request; the grant survives only while the session
  object lives.

### Task 2 — wire the gate into both tools

- `SshShellExecutor` resolves the host (broken registry/unknown alias first),
  then the gate, then the pool/channel; pass `exec.agent.session`, toolName,
  callId, signal.
- `ssh_scp` does the same before resolving local paths or dialling; a gate
  failure is the structured `{ok:false, error:{phase:'approval', alias, message}}`
  result.
- No connection is dialled and no channel opened on a rejection; tests assert
  the fixture saw no connection for both tools.
- `approval` is recorded-not-enforced only until this task lands; after it, the
  docs must say enforced.

### Task 3 — approval request mapping + fail-closed behaviour

- Map `allowed-once` to the session grant; `rejected` and `cancelled` to a
  "not authorized" error; `unavailable` to the missing-answerer message with the
  `trusted` escape hatch; session policy "never" to a deterministic rejection.
- The request reason names the alias, user@host:port, the session scope and the
  consequence; displayReason is the human sentence.
- Abort during a pending request settles as cancelled and releases the call.
- Tests: each outcome, abort mid-request, no dial on any non-allow outcome,
  one request under concurrent misses, message contents.

### Task 4 — the dedicated approval card (client half)

- Register a `conversation.composer` chain entry at priority 0 in
  `lib/client.js` (generated client registry must carry it). Match only pending
  approvals whose toolName is `ssh_shell` or `ssh_scp`; render a card naming
  the alias/user@host:port and "allow for this session" / "reject".
- Answer through the pending approval's `answer('allowed-once'|'rejected')`; no
  new channel. Remove the entry when the pending approval settles.
- Audit: generated registry entry, priority 0, matcher only for the two tool
  names, no match for other tools, render handles both outcomes and a settled
  pending; boot the row in an isolated DSH instance to prove the slot renders
  (per the cross-plugin slot rule).
- No page navigation; dictionaries are strings; inject only measured ids.

### Task 5 — docs

- configuration.md/architecture.md/README(s): `approval: trusted|session`,
  session-memory semantics, fingerprint invalidation, fail-closed outcomes, the
  dedicated card, terminal out of scope. Remove "recorded, not enforced".
- No RELEASE_NOTES version bump (Plan 4).

## Acceptance

- Audit + npm test green on a clean tree after each task; no push/version bump.
- A rejection never dials; a trusted host never prompts; a grant is reused in
  one session and asks again in another; fingerprint edits re-prompt.
- The card appears for ssh_shell/ssh_scp pending approvals only and answers
  allowed-once/rejected; other approvals still use the platform card.
- Existing Plan 1/2 behaviour unchanged.
